## T4-compatible kernel choice

The loader now creates an in-memory source-equivalent kernel module on sm75 and
keeps the installed package untouched. Its backward tiles are reduced from
`(16, 64, 64, 16)` to `(16, 16, 16, 16)`, with one pipeline stage.

Offline Triton compilation for target `sm75` measured:

| Backward tiles | Shared memory |
| --- | ---: |
| `(16, 64, 64, 16)` | 147456 bytes |
| `(16, 32, 32, 16)` | 81920 bytes |
| `(16, 16, 16, 16)` | 49152 bytes |

The patched loader also passed real forward/backward execution on the local
RTX 3050 through the same adapter, including D256 GQA and a non-multiple
sequence length. A local end-to-end one-step SFT rehearsal then passed with an
unequal padded batch and the hybrid GDN/causal-convolution path. The rehearsal
found two integration issues before the live run: TRL requires either
`attention_mask` or `position_ids`, so the padded collator now supplies dense
`position_ids` while still omitting `attention_mask`; and Accelerate's
`GradScaler` rejects FP16 trainable gradients, so T4 keeps LoRA parameters in
FP32 while the base model runs under FP16 autocast. These are local integration
checks only; neither is a T4 result.
